# HTML design

Use a semantic, readable layout that supports the learner’s actual study tasks. A unit does not need a fixed collection of boxes or interactions. Choose components based on the material: headings and paragraphs for teaching, tables for comparisons, inline SVG or simple HTML for diagrams, and `<details>` for answers the learner wants to reveal.

Keep the file self-contained when it must work offline. Do not load diagram renderers, fonts, or other scripts from a CDN. Static diagrams can be drawn with inline SVG, CSS, or HTML; include a text explanation when the visual alone is ambiguous. When the prose teaches a curve or a shift, show the actual graph near that explanation. Label axes, curves, old and new equilibria, and the direction being claimed. Compute marked points from the same equations or paths used to draw the curves; a misplaced marker can reverse the lesson.

Place a graph after its section heading and a short introduction, not between a section kicker and its heading. For inline SVGs in reading views, avoid a `<title>` child when a hover tooltip could cover the plot. Give the SVG an accessible `aria-label`, keep a `<desc>` for screen readers, and put the visible explanation in the `figcaption`. Check the graph while hovering over its data marks as well as in a static screenshot.

For interactive controls, ensure the page still communicates the content without JavaScript, and test the controls if you include them. Keep print styles useful: preserve headings and formulas, avoid splitting short callouts where possible, and make hidden answers visible on paper when that suits the learner’s use. Closed details elements can remain hidden in browser print output despite CSS display rules. When answers should print, open them in a beforeprint handler, restore their prior state afterprint, and confirm the answers appear in the rendered PDF. If numbered steps contain inline math with subscript or superscript tags, keep the whole sentence in one layout item. A grid applied directly to an li can promote those inline tags into separate grid cells when printed.

Match language and register to the learner. Use responsive widths, readable type sizes, sufficient contrast, and semantic headings in syllabus order.

When the learner requests true/false, single-choice, or multiple-correct questions in an HTML guide, provide selectable controls and immediate grading with explanations. An answer accordion alone is not an interactive quiz. Use radio groups for one answer and checkboxes for multiple answers. Grade multiple-correct questions by exact set equality, rejecting both missing correct choices and extra wrong choices. Test empty submissions, correct and wrong answers, reset, keyboard controls, and print behavior in a browser.

Keep each practice prompt visible before revealing its solution. Put only the answer inside a details element labeled “Ver respuesta”; placing both the prompt and answer inside the same details element reveals the solution as soon as the learner opens the question. Verify the initial closed state and open/close behavior after rebuilding the final HTML.

Assess subject understanding rather than recall of old exam results. Every quiz prompt must include the data and assumptions needed to answer it. Never refer to an absent graph, an exam year, or a guide exercise as a substitute for those premises. If a graph is essential, display it beside the question; otherwise describe the economic change directly. Expand unfamiliar abbreviations, use plausible conceptual distractors, and explain the causal reasoning rather than merely giving the correct letter. Balance true and false statements so answer patterns do not replace learning.
